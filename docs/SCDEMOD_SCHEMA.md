# .scdemod package contract (schema 1)

This is the package contract implemented by SCDE Mod Manager. It describes package metadata, not the Script Extender `info.json` format. Packages without `schemaVersion` remain valid legacy schema-1 packages. An explicitly unsupported schema version is rejected, not silently interpreted as schema 1. Older manager releases do not enforce the new dependency-range or persistence fields; authors using these fields should require the issue-1-fix release or later.

## Archive layout

`.scdemod` is a ZIP archive with `manifest.json` at its root and at least one file inside `payload/`. Payload paths are relative to the **modded game copy**, never to the original Steam installation. Use `/` in ZIP entry names. Absolute paths, parent traversal, Windows device names, alternate streams, trailing dots/spaces, internal `.` or empty path segments, and case-insensitive duplicate archive entries are rejected before extraction. A single leading `./` and directory entries ending in `/` remain accepted for legacy archives.

```text
manifest.json
payload/
  BepInEx/plugins/example.mod/plugin.dll
  BepInEx/plugins/example.mod/settings.default.json
```

## Manifest

```json
{
  "schemaVersion": 1,
  "id": "example.mod",
  "name": "Example Mod",
  "version": "1.2.0",
  "author": "Example Author",
  "description": "A short explanation of the Mod.",
  "gameVersion": "Tested game build",
  "dependencies": [
    { "id": "bepinex-runtime", "version": "5.4.23.5" },
    { "id": "shcde-script-extender", "minimumVersion": "2.6.0", "maximumVersion": "2.8.0" }
  ],
  "persistentPaths": {
    "version": 1,
    "paths": ["BepInEx/plugins/example.mod/settings.json"]
  }
}
```

| Field | Contract |
| --- | --- |
| `schemaVersion` | Optional integer `1`; omitted means `1`. |
| `id` | Required stable ID: 2–64 lowercase letters, digits, `.`, `_`, `-`, beginning with a letter or digit. Windows device names (`con`, `nul.txt`, etc.) and trailing dots are not allowed. Changing the ID creates a different installed Mod. |
| `name`, `version` | Required non-empty strings; surrounding whitespace is trimmed. `name` is for display. Exact dependency checks use `version`; numeric update/range comparisons have the rules below. |
| `author`, `description`, `gameVersion` | Optional display strings. `gameVersion` is informational, not an executable-build compatibility guarantee. |
| `dependencies` | Optional array, default `[]`; unique dependency IDs, no self-dependencies. Runtime dependency cycles are rejected. |
| `persistentPaths` | Optional, versioned opt-in declaration of mutable data in a package-owned plugin directory. See below. |

Unknown fields are not retained by normalization and must not be used for mandatory behavior. Fields generated by the manager are not author-controlled features: `packageSha256` records the SHA-256 of imported archive bytes; `scriptExtender` is used by the SE importer to retain the upstream GUID, SE version bounds, metadata version and update URL. A package-provided SHA-256 is not trusted as proof of its own contents.

## Dependency versions

Each dependency requires an `id` and uses one of these forms:

```json
{ "id": "another.mod" }
```

Any installed version. The manager's normalized representation may include `"version": ""`; reloading that legacy representation is supported.

```json
{ "id": "another.mod", "version": "1.2.0" }
```

Exact string equality, preserving the old contract. `1.2` is **not** the exact version `1.2.0`, and `2.8.0` is not the exact version `2.8.0+scdemm.1`.

```json
{ "id": "another.mod", "minimumVersion": "1.2.0", "maximumVersion": "1.9.0" }
```

Inclusive numeric bounds. Either bound may be omitted; a supplied bound must be a supported, non-empty version string. Minimum greater than maximum is invalid. A non-empty exact `version` cannot be combined with bounds. Wildcards, caret/tilde expressions and compound ranges are not supported.

Range and update comparisons support dotted numbers (including `5.4.23.5`), optional leading `v`, prerelease suffixes, and `+build` metadata. Missing numeric components compare as zero. Prereleases precede the corresponding final release; build metadata does not affect precedence. An unrecognized installed version cannot satisfy a numeric range. Consequently `2.8.0+scdemm.1` satisfies an inclusive maximum of `2.8.0`, without claiming that the adaptation is proven compatible with every SE release.

## Mutable plugin data

`persistentPaths` has an independent `version: 1` and a `paths` array. Paths use `/` (input `\` is normalized), are relative to `payload/` / the game-copy root, and identify an exact file or a subdirectory. Wildcards, absolute paths, `.`/`..` segments, empty segments, Windows device names, alternate streams, trailing dots/spaces, and duplicate or overlapping declarations are rejected.

The deployment ownership check is deliberately narrower than the syntax:

- A declaration must be strictly inside `BepInEx/plugins/<owned-folder>/`, not the entire plugin folder.
- The package must actually own that folder through its payload inventory, and must not share it with another package.
- Executable/plugin payloads such as `.dll`, `.exe`, `.so`, `.dylib`, `.pdb`, `.semod`, `.map`, `.lua`, and `.luac` are not mutable settings; declarations cannot preserve these as user data.
- `BepInEx/config/` already uses the manager's shared configuration-preservation path and needs no declaration.
- Reserved runtime, SE, and multiplayer-component files are not made writable by a declaration. Collisions with another package's files are rejected rather than resolved by silently overwriting them.

Generate the declared settings file at runtime, or ship a template at a different path (for example `settings.default.json`). Existing mutable data is preserved across deployment/rebuild/update. If a package also supplies content at a path occupied by that saved data, deployment fails clearly before overwriting either side; this applies even when the package owns the settings. The existing `BepInEx/config/` default-file exception is unchanged. A missing declaration does not request arbitrary persistence of a plugin's directory. Legacy SE lobby-setting migration is limited to `*.msgpack` / `*.bin` in verified SE-related plugin directories, including the specifically verified Fixes layout; it is not a general whole-plugin backup rule.

## Same-version Workshop revisions

During background checks the manager still reads package metadata first. It hashes complete `.scdemod` archives only when all of these are true:

1. The ID is already installed and is not an excluded built-in component.
2. The candidate has the same version (exact label or equivalent numeric precedence).
3. The installed record contains a valid SHA-256 from an earlier import.

Hashing is streamed and cancellable; it does not decompress the payload or run the Mod. Different bytes with the same version produce a **content-changed** update candidate. The player still chooses whether to install it. A higher version remains a normal update candidate without this additional hashing step. Uninstalled Mods, older versions and legacy records without a stored digest do not trigger speculative content-change reminders. Re-importing a legacy package establishes its digest for future checks.

The digest covers the archive itself: a repack with different compression/ZIP timestamps can therefore be offered even if extracted gameplay files are unchanged. It detects change, not publisher identity, malware or multiplayer safety. Prefer increasing the package version for intentional releases.
